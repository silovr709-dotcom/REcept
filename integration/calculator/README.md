# Мост «калькулятор → личный кабинет». Что скопировать в калькулятор

Эта папка — **готовый код для репозитория калькулятора** (`silovr709-dotcom/Calculator`).
Он лежит здесь, а не там, потому что у меня нет прав на запись в тот репозиторий.
Файлы можно скопировать как есть: они проверены — PHP разбирается без ошибок,
TypeScript собирается (`tsc -b` без замечаний), тесты карты данных проходят (21 из 21).

Сторона кабинета уже работает: миграция `supabase/migrations/0002_integration.sql`
применена к живой базе, 44 проверки моста и 31 прежняя проверка прав прошли.

## 2. Три строки в `server/api/index.php`

Подключение рядом с существующим `require`:

```php
require __DIR__ . '/core.php';
require __DIR__ . '/cabinet.php';   // ← добавить
```

И перед последней строкой файла — там, где сейчас стоит
`recept_fail(404, 'Неизвестный запрос к API: ' …)`:

```php
recept_cabinet_route($route . ' ' . $method);   // ← добавить

recept_fail(404, 'Неизвестный запрос к API: ' . ($route === '' ? '(пусто)' : $route));
```

Функция сама отвечает и завершает работу, если маршрут её; если нет — просто
возвращает `false`, и всё работает как раньше.

## 3. Ключи в `api/config.php` на хостинге

Этот файл не выкладывается из репозитория (он в исключениях FTP) — его правят
прямо на сервере. Добавить три строки:

```php
<?php
return [
    'dataDir' => '…',            // уже есть, не трогать

    // Личный кабинет клиентов
    'cabinetUrl'    => 'https://iswkzclegjcbhxaatmbb.supabase.co',
    'cabinetSecret' => 'sb_secret_…',   // ключ calculator_bridge, см. ниже
    'cabinetSite'   => 'https://рецепт-тверь.рф',
];
```

**Где взять `cabinetSecret`.** В Supabase уже создан отдельный ключ с именем
`calculator_bridge` (Project Settings → API Keys). Нажать «Reveal», скопировать
значение целиком. Этот ключ:

* обходит все ограничения базы — поэтому он живёт **только** в `api/config.php`
  на хостинге, его нельзя класть в репозиторий и нельзя отдавать в браузер;
* если он когда-нибудь утечёт, его удаляют одной кнопкой там же и создают новый —
  остальные ключи при этом не меняются.

Проверка после настройки: войти в калькулятор и открыть
`/api/index.php?r=cabinet/health` — должно быть `"configured": true`.

## 4. Кнопка в интерфейсе

Весь обмен уже собран в одной функции. Минимальная кнопка:

```tsx
import { publishToCabinet } from '../lib/cabinetApi';

const sendToCabinet = async () => {
  const blob = await buildClientOfferDocx(documentArgs);   // как и для скачивания
  const result = await publishToCabinet({
    project,
    profile: clientProfile,          // findClientForProject(project, clients)
    kind: 'offer',                   // offer | specification | contract | receipt | sketch | package
    blob,
    fileName: `${project.name} — КП.docx`,
    rollup: clientRollup,            // buildClientOfferRollup(details)
    total: offerTotal,
  });
  toast.info(`Отправлено клиенту. Версия ${result.version}.`);
};
```

В `ClientView.tsx` документы уже проходят через одну воронку — `keepDocument(kind, name, blob)`
(строка ~561). Проще всего добавить кнопку «Отправить в кабинет» рядом со
скачиванием и переиспользовать тот же `blob`. Компоненту нужен профиль клиента:
он получается из состояния через `findClientForProject(project, clients)` из
`lib/clientProfiles`.

Остальные функции `cabinetApi.ts`:

| Функция | Зачем |
| --- | --- |
| `cabinetHealth()` | настроен ли мост — по этому ответу прячется кнопка |
| `publishToCabinet(…)` | выгрузить данные проекта и положить документ клиенту |
| `syncProjectToCabinet(…)` | обновить состав, оплаты и этапы без документа |
| `inviteClientToCabinet(…)` | получить ссылку-приглашение в кабинет |
| `cabinetProjectStatusInfo(id)` | видел ли клиент, согласовал ли, есть ли вопросы |
| `cabinetEvents(since)` | что сделали клиенты: согласования, вопросы, первый вход |

## 5. Что уходит клиенту, а что не уходит никогда

Границу задаёт `cabinetPayload.ts`, и на неё есть тесты.

**Уходит:** имя, телефон, почта клиента; название и адрес проекта; состав заказа
построчно; одна итоговая сумма; внесённые оплаты; даты замера, готовности,
доставки, монтажа; сам файл документа.

**Не уходит:** себестоимость, наценка, маржа, цена за отдельную строку, бланк на
фабрику, комментарии менеджера, причина отказа, паспортные данные, аналитика,
фотографии замера. Последний тест в `cabinetPayload.test.ts` прямо проверяет, что
ничего из этого не попадает в отправляемые данные.

## 6. Как устроена отправка документа

1. `integration_publish_begin` — база заводит карточку документа и бронирует
   номер версии и путь к файлу. Документ пока не опубликован, клиент его не видит.
2. PHP заливает файл в закрытое хранилище по выданному пути.
3. `integration_publish_finish` — размер файла, версия становится действующей,
   документ публикуется; если он требует согласования, он переходит в «на согласовании».
4. Если заливка сорвалась — `integration_publish_abort`, и в кабинете не остаётся
   ни пустой карточки, ни пустой версии.

Повторная отправка того же документа — это **новая версия**: прежняя остаётся в
истории. Если версию уже согласовали, подменить её файл база не даст, а появление
новой версии снимет отметку «согласовано» и попросит согласовать заново.

Все вызовы моста проходят только по служебному ключу: клиент или посторонний,
даже зная адрес базы, выполнить их не может — проверено на живой базе.

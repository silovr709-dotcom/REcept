# Личные кабинеты «РЕцепт» — как включить

Коротко: сайт лежит на GitHub Pages, своего сервера у него нет. Поэтому
кабинет работает на отдельной базе **Supabase** — это управляемый
PostgreSQL с авторизацией и хранилищем файлов. Все права доступа живут
внутри базы (Row Level Security), а не в браузере: даже если подставить
чужой идентификатор руками, база ничего не отдаст.

Пока база не подключена, кабинет честно пишет посетителю, что он ещё не
работает, и никуда не отправляет данные. Ничего «понарошку» не
показывается.

---

## 1. Что нужно сделать один раз (20–30 минут)

### Шаг 1. Завести проект Supabase

1. Откройте <https://supabase.com>, войдите через GitHub.
2. **New project**. Имя — `recept-kabinet`. Регион — **Frankfurt (eu-central-1)**:
   ближе всего к Твери, меньше задержка.
3. Пароль базы данных придумайте длинный и сохраните в менеджере паролей.
   Он нужен редко, но восстановить его нельзя.
4. Бесплатного тарифа хватает: 500 МБ базы, 1 ГБ файлов. Когда файлов
   станет больше, тариф Pro стоит порядка 25 $ в месяц.

### Шаг 2. Выполнить миграцию

1. В проекте Supabase слева → **SQL Editor** → **New query**.
2. Скопируйте туда **целиком** файл `supabase/migrations/0001_cabinet.sql`
   из этого репозитория и нажмите **Run**.
3. Скрипт создаёт 16 таблиц, правила доступа, закрытое хранилище
   `project-files` и типовые 13 этапов проекта. Выполнять его повторно
   безопасно — он написан идемпотентно.

### Шаг 3. Настроить вход по почте

**Authentication → Sign In / Providers → Email**:

* `Confirm email` — **включить** (подтверждение почты).
* `Secure email change` — включить.
* Минимальная длина пароля — 8.

**Authentication → URL Configuration**:

* `Site URL`: `https://silovr709-dotcom.github.io/REcept/kabinet/`
* `Redirect URLs` — добавить обе строки:
  * `https://silovr709-dotcom.github.io/REcept/kabinet/vhod/`
  * `https://silovr709-dotcom.github.io/REcept/kabinet/*`

Письма на бесплатном тарифе отправляет сам Supabase, но с жёстким
лимитом (несколько штук в час) и с чужого адреса. Для нормальной работы
в **Authentication → Emails → SMTP Settings** пропишите почтовый сервис
(подойдёт тот же ящик `tver-kuhni11@yandex.ru` через SMTP Яндекса).
Пока SMTP не настроен, выдавайте доступ **персональной ссылкой** из
карточки клиента — она работает без писем вообще.

### Шаг 4. Вписать адрес и публичный ключ в сайт

1. **Project Settings → API**. Скопируйте:
   * `Project URL` — вида `https://abcdefgh.supabase.co`;
   * ключ **anon / publishable** (не `service_role`!).
2. Откройте в репозитории файл `public/kabinet-config.js` и впишите их:

   ```js
   window.__RECEPT_CABINET__ = {
     url: 'https://abcdefgh.supabase.co',
     anonKey: 'eyJhbGciOi...',
   };
   ```

3. Сохраните, закоммитьте, выполните `npm run build:static` и отправьте
   изменения — через пару минут кабинет оживёт на сайте.

> **Ключ `service_role` (secret) нельзя класть в этот файл никогда.**
> Он обходит все правила доступа и открывает базу целиком. Ключ `anon`
> публичный по замыслу: сам по себе он не даёт ничего, каждую строку
> проверяет база.

### Шаг 5. Сделать себя сотрудником

Роль сотрудника нельзя получить из кабинета — это защита от того, чтобы
клиент «назначил себя администратором». Поэтому первый раз её выдают
прямо в базе:

1. Зарегистрируйтесь в кабинете как обычный пользователь:
   `https://silovr709-dotcom.github.io/REcept/kabinet/` → «Я впервые».
2. В Supabase → **SQL Editor** выполните (подставьте свою почту):

   ```sql
   update public.profiles set role = 'admin'
   where email = 'tver-kuhni11@yandex.ru';
   ```

3. Так же заводится вторая учётная запись: Роберту и Кате лучше иметь
   по своей, чтобы в журнале было видно, кто что сделал. Роль `admin` —
   полные права, `staff` — то же самое, кроме смены ролей.

## 2. Как это устроено внутри

### Таблицы (16)

| Таблица | Зачем |
| --- | --- |
| `profiles` | учётная запись: имя, телефон, роль, блокировка |
| `clients` | карточка заказчика (это не учётная запись) |
| `client_users` | кто из пользователей относится к карточке |
| `projects` | проект: кухня, гардеробная, ванная |
| `project_members` | допуск пользователя к проекту и право согласования |
| `project_invites` | приглашения: токен, срок, отзыв |
| `project_stages` | 13 этапов, сроки, комментарии |
| `documents` | карточка документа: категория, состояние, публикация |
| `document_versions` | версии файлов, номер, актуальность |
| `approvals` | решения клиента: кто, когда, по какой версии |
| `project_notes` | договорённости; видимость «клиент / внутреннее» |
| `project_messages` | обращения и ответы |
| `project_costs` | состав стоимости |
| `project_payments` | график платежей |
| `notifications` | события в кабинете и счётчик непрочитанного |
| `audit_logs` | журнал: загрузки, публикации, согласования, этапы |

### Хранилище

Один закрытый бакет **`project-files`**, лимит 25 МБ на файл, разрешены
PDF, JPG, PNG, WEBP, HEIC, GIF, DOC/DOCX, XLS/XLSX, TXT, ZIP.
Путь файла: `projects/<проект>/<документ>/<случайное имя>.<расширение>`.

Публичных ссылок на файлы не существует. Кабинет каждый раз просит у базы
**подписанную ссылку на 5 минут**, и только если у человека есть доступ к
проекту, а документ опубликован.

### Правила доступа

* RLS включён (и `force`) на всех 16 таблицах. Политик «для всех» нет ни одной.
* Клиент видит проект, только если есть строка в `project_members`.
  Регистрация сама по себе не даёт ничего.
* Клиент видит документ, только если `is_published = true`; строку сметы
  и платёж — так же; заметку — только с видимостью «клиент».
* Повысить себе роль через кабинет невозможно: политика на `profiles`
  разрешает менять свои данные, но не поле `role`.
* Согласованную версию файла нельзя подменить — только выпустить новую,
  и она снова уходит на согласование.
* Журнал `audit_logs` пишется триггерами и доступен только сотрудникам.

## 3. Проверка безопасности

В каталоге `supabase/tests/` лежит готовый набор проверок —
31 утверждение, повторяющее сценарии приёмки: два клиента и
администратор, подстановка чужого идентификатора в адресе, попытка
повысить себе роль, доступ анонима, закрытие файла при снятии публикации.

**На живом проекте Supabase:** откройте SQL Editor и выполните
`supabase/tests/policies-test.sql` целиком. Скрипт создаёт тестовые
записи и в конце **откатывает** их (`rollback`) — следов не остаётся.
Любое нарушение правил роняет скрипт с понятным сообщением по-русски.

**Локально, на обычном PostgreSQL 15+** (так это проверяли при разработке):

```bash
psql "$DB" -v ON_ERROR_STOP=1 -f supabase/tests/local-shim.sql
psql "$DB" -v ON_ERROR_STOP=1 -f supabase/migrations/0001_cabinet.sql
psql "$DB" -v ON_ERROR_STOP=1 -f supabase/tests/policies-test.sql
```

`local-shim.sql` подменяет то, что в Supabase есть по умолчанию (схемы
`auth` и `storage`, роли `anon` / `authenticated`, функция `auth.uid()`).
В настоящем проекте он не нужен.

Если под рукой нет сервера PostgreSQL, его можно поднять одной командой
из Python: `pip install pgserver`, затем
`python -c "import pgserver,pathlib; print(pgserver.get_server(pathlib.Path('/tmp/pgdata')).get_uri())"`.

## 4. Повседневная работа

1. **Панель** — `/kabinet/admin`: поиск по клиентам и проектам, новые
   клиенты и проекты, открытые вопросы, журнал действий.
2. **Новый клиент** → в его карточке **«Пригласить в кабинет»** →
   персональная ссылка (действует 30 дней, одноразовая). Её можно
   скопировать или сразу открыть письмо с готовым текстом.
3. **Проект** → вкладки: документы, эскизы, этапы, заметки, деньги,
   вопросы, доступ.
4. Документ сначала живёт черновиком — клиент его не видит. Галочка
   «Опубликовать» открывает документ и создаёт клиенту уведомление.
5. Эскиз на согласование: категория «Эскиз», публикация и отметка
   «Нужно согласование». Клиент нажимает «Согласовать» или «Запросить
   изменения» — решение записывается с версией, временем и автором.
6. Этапы: статус, плановая и фактическая даты. Пока даты нет, клиент
   видит «Дата уточняется» — ничего не выдумывается.

### Если нужно закрыть доступ

Вкладка **«Доступ»** в проекте: «Убрать» — снимает допуск к проекту,
«Заблокировать» — закрывает человеку кабинет целиком, мгновенно и для
всех проектов. Данные при этом не удаляются.

## 5. Чего здесь нет

* **Онлайн-оплаты.** Суммы и платежи вносит мастерская вручную; кабинет
  ничего не считает по непроверенным данным и прямо пишет, если сумма
  ещё не внесена.
* **Писем о событиях.** Уведомления пока только внутри кабинета, со
  счётчиком непрочитанного. Рассылку включим, когда будет настроен SMTP —
  архитектура (таблица `notifications`) к этому готова.
* **Чата.** Обращения — это вопросы и ответы по проекту с историей, а не
  мессенджер.
